The Himmel Adoption Trail

Himmel adds safety rails and helpers to Claude Code, Anthropic's AI coding assistant. Before anything else this page tells you what you need and what the install does that you cannot easily take back; it then answers three questions, gives you a five-minute way to try it on a throwaway project, and lays out the full trail for going further.

Before you install

Six things that decide whether to run the install at all. Each is here, not further down, because you cannot easily take it back afterwards. Question 2 below has the full list of changes.

1. You need a way to sign in to Claude Code

Claude Code only runs once you are signed in. Anthropic's documentation lists a Claude subscription (Pro, Max, Team or Enterprise), a Claude Console account, or a supported cloud provider such as Amazon Bedrock. It does not say whether a free claude.ai plan is enough, so check Anthropic's sign-in page before you start. The first time you run claude it opens a browser to sign in. Step 1 of the first 5 minutes ends by asking you to do that, so a sign-in problem shows up before himmel is involved.

2. The install overwrites files in your project's scripts folder

The starter install copies 13 helper scripts into the project's scripts/ folder: hooks/auto-approve-safe-bash.sh, hooks/block-edit-on-main.sh, hooks/block-read-secrets.sh, hooks/check-commit-msg.sh, hooks/check-worktree-isolation.sh, hooks/check-push-target.sh, guardrails/lib.sh, guardrails/guard-gh.sh, lib/py-armor.sh, clean-garden.sh, worktree.sh, clean.sh and _new-worktree.sh. If a file with one of those names is already there, it is replaced in place: no backup is made, and no record is kept of which files were yours. In a test, a committed scripts/worktree.sh was replaced by himmel's version. Run the install in a project where git status shows nothing uncommitted, so git can bring anything back. The same install also replaces the project's statusLine setting (item 6).

3. The git checks may not check anything

The install places three git hooks: one before a commit, one on the commit message and one before a push. With the pre-commit tool present, those hooks run whatever checks your project lists in a .pre-commit-config.yaml file, and the starter install does not create one. In a test of a starter install, a commit whose message was neither conventional nor carried a ticket reference succeeded, and so did a push to main. So do not count on the install to refuse a push to main or to check commit messages. If pre-commit cannot be installed, the installer places plain git hooks instead; this page has not verified what those enforce. What does work in a starter install is the Claude Code side: inside a Claude Code session, editing a file on the default branch is refused.

4. Commit trailers belong to himmel's own repository

Himmel's own repository asks that a change's first commit end with two trailer lines (extra lines at the end of a commit message), Platforms tested: linux and Security reviewed: manual, and checks them when you push. Those checks live in himmel's own .pre-commit-config.yaml. A starter install neither copies nor enables them, so your project is not asked for trailers. You will meet them if you contribute a change to himmel itself; Level 1 says more.

5. Minimum versions

The installer checks that the tools are present, not which version. Older versions can fail later. The minimums himmel documents (from setup/new-machine.md): git 2.30, bash 3.2, python3 3.10, jq 1.6, node 18 to build (20.17 to push), npm 11 (only for pushing), pre-commit 3.5, and the latest claude. Check what you have:

git --version
node --version
npm --version
jq --version
python3 --version
claude --version

Each prints a version number. On one Linux machine claude --version printed 2.1.278 (Claude Code): a version followed by (Claude Code). Where a step below lists no expected output, we did not capture one.

6. What Claude Code does with the files the install writes

Four Claude Code behaviours the install relies on, none of them himmel's own:

  • Workspace trust. In an interactive session Claude Code holds back hooks from every settings file until you accept its trust dialog for the folder. The install records that trust in ~/.claude.json for the project folder; if it cannot, it says so and you accept the dialog the first time you run claude there. Until then the hooks it wrote do nothing.
  • Settings files and scope. Claude Code reads ~/.claude/settings.json (yours, for every project), .claude/settings.json in the project (meant to be committed and shared) and .claude/settings.local.json (personal, kept out of git). List settings and hooks from several files are combined; a single-value setting set in more than one file takes the more specific one (local, then project, then yours). --scope project writes the shared project file, and the install puts machine-specific paths in it (the status line command and HIMMEL_REPO point at your himmel download), so think before you commit that file. See Anthropic's settings page.
  • One status line. statusLine is a single setting, not a list. Himmel's install sets it in the project file and overwrites any statusLine that file already had.
  • Marketplaces. A plugin marketplace is a catalog of plugins. Using one takes two steps: add the marketplace, then install plugins from it. The install registers four marketplaces (Claude Code keeps that list once per user, not per project) and installs 14 plugins for the project: 5 left on, 9 installed but off until you enable them. Anthropic's documentation warns that plugins can run arbitrary code with your user privileges, so install from marketplaces you trust.

Start here: three questions

In the order you would ask them. Nothing on this page changes your machine until you run a command yourself.

Question 1

What is this?

Himmel is a set of add-ons for Claude Code — Anthropic's AI coding assistant, which you run in a terminal — that makes the assistant safer and more repeatable to work with. It does this with small scripts that fire automatically and refuse risky actions (editing your main branch, reading your secret files, pushing unreviewed work), so the rules hold even when nobody remembers them. Around that it adds helpers for the routine work: a separate working folder for every task, pull-request review, and written notes so a job can carry on in a later session.

Four words you will see straight away. A hook is a small script Claude Code runs automatically before or after it uses a tool, and it can refuse the action. A gate is a check that must pass before a commit, a push or a merge is allowed. A worktree is a second working folder on its own git branch that shares your repository's history — the “separate working folder” above. A handover is a written note that lets a later session pick up where an earlier one stopped.

Who it is for

Developers who already use git and a terminal and want Claude Code to work with guardrails on. You do not need to know Claude Code or himmel beforehand; you do need to be comfortable running commands in a terminal. Linux and macOS are supported. Windows is an early alpha — see the boxes in the first 5 minutes. Try it on one throwaway project before you point it at anything you care about.

Question 2

What will it do to my machine?

Run from a project folder, the starter install (--scope project) makes exactly the changes below. Adding --dry-run to the himmelctl install command prints only a one-line summary and writes nothing; it does not list the files. To preview the file-level plan, run the installer script it wraps (from the project folder, with himmel downloaded to ~/himmel as in the first 5 minutes):

bash ~/himmel/scripts/adopt.sh --profile core --scope project --dry-run

In the project folder you run it from

  • Copies 13 helper scripts into the project's scripts/ folder (the hooks and the worktree commands), overwriting any file of the same name — see item 2 of Before you install for the list.
  • Adds to the project's .claude/settings.json: three hook entries (they refuse edits on your default branch, refuse reading secret files such as .env, and auto-approve a short list of safe shell commands), a status line (replacing any statusLine already set there), and a HIMMEL_REPO setting that points back at the himmel download, plus one more environment setting the status line needs (CLAUDE_HUD_ALLOW_EXTRA_CMD).
  • Places three git hooks in .git/hooks — one before a commit, one on the commit message, one before a push. If you already had git hooks, each is saved next to it as <hook>.himmel-backup and put back on uninstall. If the pre-commit tool that installs them is missing, the installer tries to install it; if that fails it falls back to plain git hooks without the lint checks and says so. Placing the hooks is not the same as enforcing anything: see item 3 of Before you install.
  • Installs 14 Claude Code plugins (add-on packs of slash commands and skills) for this project, from four plugin marketplaces it registers first. Five are switched on and nine are installed but left off until you enable them.

In your home folder

  • Appends a marked block of four short working principles (think before coding, simplicity first, surgical changes, goal-driven execution) to ~/.claude/CLAUDE.md and ~/.codex/AGENTS.md. It creates the file if it is absent, skips it if the block or those principles are already there, and never overwrites what you wrote.
  • Writes a small himmelctl launcher to ~/.local/bin and keeps its own cache in ~/.claude/himmel.
  • Writes the status line's settings file, ~/.claude/plugins/claude-hud/config.json, replacing one that is already there.
  • Records in ~/.claude.json that you trust this project folder, so Claude Code does not ignore the settings the install just wrote. If it cannot write that entry, the install summary says so and you accept the trust prompt the first time you run claude there.

Inside the himmel download

  • Builds himmel's Jira command-line tool (npm install then npm run build). This needs the network.

Only if bun is installed

  • Installs the qmd search tool, downloads about 2.1 GB of search models, and indexes the himmel download. Without bun this whole step is skipped.

Left alone

The starter install does not touch your notes vault (a folder of Markdown notes, usually opened in Obsidian), does not arm any cadence (a recurring scheduled job that himmel sets up with your operating system's scheduler), does not set up the Telegram bridge, and leaves the optional review lanes off. A lane is a backend — an AI model plus its tooling — that himmel can run work on; the review lanes give a second opinion on your changes, and without them review runs on Claude alone.

What changes about how you work

  • Inside a Claude Code session, editing a file while you are on the default branch is refused; you make a worktree first with the /worktree command. That refusal is the point.
  • Nothing else about committing or pushing changes by default. The git hooks are in place, but when the pre-commit tool is present a starter install gives them no checks to run (item 3 of Before you install), so commit-message and push-to-main rules are yours to add.

Prefer to gate every project on the machine instead of one? Use --scope user, which wires the same hooks into ~/.claude/settings.json so they apply to every project you open — including ones you did not mean to gate. Try project scope first.

Question 3

How do I undo it?

Run the uninstaller from the same project folder you installed into. It prints what it is about to touch and asks Proceed? [y/N]; anything but y stops it, and with no terminal attached and no --yes it refuses rather than guess. If a step cannot finish it says so and exits non-zero instead of claiming success. The commands assume himmel is downloaded to ~/himmel, which is what step 3 of the first-5-minutes path below does.

# preview only: prints the footprint and changes nothing
node ~/himmel/scripts/himmelctl/bin.js uninstall --dry-run
# the real thing (asks before it acts)
node ~/himmel/scripts/himmelctl/bin.js uninstall

Removed

  • The three git hooks (your own, if any, are restored).
  • Himmel's wiring in the project's .claude/settings.json and in ~/.claude/settings.json; your own settings keys are left as they are.
  • The plugins from himmel's marketplaces — this includes any of them you also enabled for your whole account — and then the marketplaces that have no plugins left.
  • The working-principles block in ~/.claude/CLAUDE.md and ~/.codex/AGENTS.md (only that block), himmel's status-line config, the scheduled jobs it armed to resume sessions (none, unless you armed some), the Telegram bridge process if one is running, its cache in ~/.claude/himmel, and, once everything else succeeded, the himmelctl launcher in ~/.local/bin.

Kept on purpose

  • Your Telegram pairing and bridge state — add --purge-state to remove them too.
  • The himmel download itself, its .env file, your worktrees and your handover notes.
  • Claude Code's own trust entry for the project, which may predate himmel — revoke it in Claude Code if you want it gone.
  • The helper scripts copied into the project's scripts/ folder. They were copied over in place with no record of which files or edits are himmel's, so the uninstaller will not guess; delete them with git if you do not want them.

First 5 minutes

The shortest safe path: a throwaway project, one install, one refusal to watch. The install downloads plugins, so how long it takes depends on your connection. Every command below assumes only what the steps before it set up.

  1. Install the tools himmel needs. You need git, node with npm, jq, python3 and the claude command (Claude Code). The installer stops and tells you if git, bash, jq, python3 or npm/bun is missing. The command-line tool gh is not needed to try himmel; it is used later, for GitHub pull requests. Pick your system:

    Linux Supported

    Debian or Ubuntu shown; on other distributions install the same tools with your package manager. Ubuntu's nodejs package ships without npm, hence the separate name. Needs sudo.

    sudo apt-get update
sudo apt-get install -y nodejs npm git jq python3
curl -fsSL https://claude.ai/install.sh | bash

    If claude is not found afterwards, open a new terminal. Recommended, so the full commit checks install:

    curl -LsSf https://astral.sh/uv/install.sh | sh
~/.local/bin/uv tool install pre-commit

    Later, for GitHub pull requests, the overnight scheduler and the extra lint checks (on Ubuntu 24.04 or newer; older releases do not package gh):

    sudo apt-get install -y gh shellcheck gitleaks at
sudo systemctl enable --now atd
sudo npm install -g npm@11

    The last line matters only when you start pushing: Ubuntu's packaged npm is too old for the push check (its registry signing key has expired). The tested end-to-end Linux walkthrough is in setup/new-machine.md.

    macOS Supported

    Assumes Homebrew. The system bash and python3 that macOS ships are too old for some himmel scripts, hence installing newer ones. These commands come from setup/new-machine.md; the end-to-end walkthrough there was run on Linux.

    brew install node git jq python bash uv
curl -fsSL https://claude.ai/install.sh | bash
uv tool install pre-commit

    If claude is not found afterwards, open a new terminal.

    Windows with Git Bash Alpha

    Experimental. The code paths exist, but they are best effort: they are not tested on every change, and there is no guarantee that an install and an uninstall round-trip cleanly. Expect quoting and path differences from Linux, and report what breaks. PowerShell versions of the scripts exist but are outside the support claim; PowerShell alone is not enough — run everything on this page in Git Bash.

    • Install Git for Windows (it includes Git Bash) from git-scm.com, then Node.js (with npm), jq and Python 3 with your usual installer.
    • Install Claude Code from PowerShell: irm https://claude.ai/install.ps1 | iex
    • Scheduled jobs use Windows Task Scheduler (schtasks) instead of at.

    Windows with WSL Alpha

    Same alpha caveats. Install Claude Code and himmel inside a WSL distribution such as Ubuntu and follow the Linux box above. Keep your projects on the Linux side (under ~), never under /mnt/c, which is very slow. Running Windows-native Claude Code with a WSL shell is not possible.

    When the installs finish, check your versions against the minimums in Before you install (git --version, node --version and so on). Then sign in: run claude, finish the sign-in in the browser it opens, and leave with /exit. Doing it now means an account problem shows up before himmel is involved. claude --version should print a version followed by (Claude Code).

  2. Make a throwaway project. Do this before the install, so your first commit does not depend on whatever git checks the install places. If git says it does not know who you are, first run git config --global user.name "Your Name" and git config --global user.email "you@example.com".

    mkdir ~/himmel-trial
cd ~/himmel-trial
git init -b main
git commit --allow-empty -m "chore: initial commit"

    Expected: git init prints Initialized empty Git repository in and the path of the new folder; the commit prints a summary line for the new commit. (We captured the first of those, not the second.)

  3. Download himmel once, next to your projects rather than inside one:

    git clone https://github.com/yotamleo/himmel ~/himmel

    Expected: git prints Cloning into and the path, and ends without an error. We captured this from a local copy, not from GitHub itself.

  4. Preview the install. Run it from the project, not from the download. Both commands below write nothing. The first is the himmelctl dry run, which prints only a summary; the second is the installer script it wraps, which lists every file and setting it would touch, so compare that one with the answer to question 2. The himmelctl command only lands on your PATH once an install has run, so the first call goes through node.

    cd ~/himmel-trial
node ~/himmel/scripts/himmelctl/bin.js install --scope project --dry-run
bash ~/himmel/scripts/adopt.sh --profile core --scope project --dry-run

    Expected from the first: a line would install (--dry-run — NOTHING below was executed): followed by + himmel (profile=starter, scope=project) and the adopt.sh command it would run. It may also warn that the Jira command-line tool is not built yet; the install builds it. From the second: one line per planned action, each starting DRY:.

  5. Install. The same himmelctl command without --dry-run. It asks no questions; the answers are the starter preset described above.

    node ~/himmel/scripts/himmelctl/bin.js install --scope project

    Expected: it ends with an install summary whose installed: list has a line + himmel (profile=starter, scope=project) and a line beginning + workspace trusted:. Before the summary it may tell you that ~/.local/bin is not on your PATH (add the line it prints to your shell profile) and, without bun, that it is skipping the search-tool wiring. We did not record how long it takes or its exit status.

  6. Watch a guardrail work. Start Claude Code in the project (you signed in at step 1; if the trust dialog appears, accept it):

    claude

    Ask it to create a file called hello.txt. The edit is refused because you are on the default branch — that refusal is the success signal. The refusal message contains block-edit-on-main: refusing to edit (we captured that by running the hook directly, not inside a live Claude Code session, and did not capture what /worktree prints). Then type /worktree feat/try-himmel (a slash command: a command you type inside a Claude Code session, starting with /) and ask again; the edit now goes through in the new worktree. Leave with /exit.

  7. Check the result. Back in the terminal, in the same project folder:

    node ~/himmel/scripts/himmelctl/bin.js status

    It prints one row for each thing himmel checks. Read the rows rather than expecting a clean board, and treat a green row as “found”, not “working”: for example, the row for the git hooks reports that the hook files exist, not that they check anything (item 3 of Before you install). We have no expected result to give you for this command. For one real working loop after this, see getting-started.md. The full install reference is setup/install.md.

  8. Undo it whenever you like with the two commands under question 3. The throwaway project and the download are yours to delete.

The full trail

Eight levels from a fresh install to a fleet that ships while you sleep. Levels 0 and 1 are guardrails for Claude Code in any project; Levels 2 to 7 describe one operator's personal setup on top of that. Climb as far as suits you — every level is optional, says what it changes, and is reversible. Click a level marker to remember where you are (kept on this device only) and any chip for its detail. Terms are explained the first time they appear and again in the glossary.

LEVEL 0

Install & stay current

This is what the first 5 minutes already did: clone github.com/yotamleo/himmel once, then run its installer from the project you want to adopt — not from inside the clone — with node ~/himmel/scripts/himmelctl/bin.js install --scope project. Leave off --scope and the installer instead reads your machine, asks — Enter always takes the safe default — and shows the full plan with --dry-run before touching anything. Once an install has run, himmelctl is on your PATH (if ~/.local/bin is), so you can shorten node ~/himmel/scripts/himmelctl/bin.js to himmelctl. Later, /himmel-update keeps everything current, including the pinned tools it manages for you. One manifest covers the whole install: dependencies, wiring, schedulers, lanes, plugins, vault and hooks.

Tools to have first: the per-system boxes in the first 5 minutes list them. The installer hard-stops on the ones it cannot work without (bash, git, jq, python3, and npm or bun) and lists the rest in its plan; gh and pre-commit are recommended rather than required to install. On an interactive terminal it will offer to install a missing hard requirement, but only after you say yes; with --dry-run or no terminal it just tells you what is missing. On Debian/Ubuntu note that the nodejs package ships without npm. Exact per-platform commands, and a verified end-to-end Linux walkthrough, are in setup/new-machine.md; the narrative version is getting-started.md.

This page ships in docs/ in the public himmel repo and is published from there at yotamleo.github.io/Himmel/adoption-trail.html; you can also open the file straight from your clone.

LEVEL 1

Ship with guardrails

The git-side discipline himmel's own repository runs on: commit checks, ticket references, attested pushes and a review loop that runs before anything merges — on GitHub via GitHub's gh command-line tool, or Bitbucket via the bundled Bitbucket CLI (the himmel-gh plugin routes to whichever your repo uses). A starter install does not turn this level on for your project: it places the git hooks but not the checks they would run (item 3 of Before you install). The installer's --contribute flag, the “development overlay”, layers himmel's own contributor setup script on top of the normal install; it is meant for working on himmel itself, and this page has not verified what it changes in another project. Two terms you will meet here: an attestation (hence “attested”) is proof written into the commit message itself, as trailer lines such as Platforms tested: linux and Security reviewed: manual, which the push gate checks; and CR is short for CodeRabbit, an automated pull-request review app — himmel's docs also say “CR findings” for the comments any reviewer leaves on a pull request. Review of a change is run by a panel: the group of reviewers — Claude, plus any review lane you switched on (Level 4) — that the /pr-check command asks to look at the same diff.

Wired by a starter install, on the Claude Code side:

  • Worktree isolation — inside Claude Code, edits on your default branch are refused
  • Secret-file protection — Claude Code is refused reading files such as .env

What himmel's own repository adds on top; none of it is in a starter install:

  • Dangerous-command blocking — destructive shell operations are refused, not regretted
  • Secret leak fences — credentials and private data are stopped before they are sent to any outside service
  • Data routing — a written policy table decides which kinds of data may be sent to which outside AI service at all; health data is refused by default
  • Attested pushes — a push carries proof of testing and review, or it doesn't leave
  • Review gates — a merge needs a clean review verdict at the exact commit being merged, not at some earlier one
  • Git-flow discipline — conventional commits with ticket refs, feature work only in worktrees, and a runbook that drives execute → review → PR → ticket → merge → handover end-to-end
  • Usage guards — unattended Claude runs use up the same 5-hour and weekly usage allowance as your own sessions, so they check it first and are gated, never silent
  • Scheduler safety — raw scheduled-task mutation is blocked; only vetted scripts arm or disarm

None of this is advice: each guard is wiring — hooks and gates that fire whether or not anyone remembers them — but only where the wiring is installed.

The git hooks (pre-commit, commit-msg, pre-push) are placed by the install — the opt-out, --skip-hooks (-SkipHooks on Windows), is a flag of scripts/adopt.sh / adopt.ps1, not of himmelctl install, so use it if you manage git hooks yourself. What they check is up to the project's own .pre-commit-config.yaml. When the commit-msg check does run, it wants a ticket reference built from your project key (the key, a dash and a number, as in your tracker's ticket IDs) when you set JIRA_PROJECT_KEY (or your own TICKET_ID_PATTERN), and a #123-style number when you have no Jira at all. TICKET_ID_REQUIRED=0 opts out of the ticket half; the conventional-commit shape check stays on either way. See setup/new-machine.md.

In himmel's own repository the git flow is structurally PR-only: its pre-push check refuses a push to main, there is one sanctioned merge path, and auto-merge is on only when you opt in. A starter install does not set that up for your project.

Impact: in himmel's own repository, nothing lands unreviewed or unattested and the workflow enforces itself, so discipline stops depending on memory at 2am. In your project you get that only for what you wire up yourself.

LEVEL 2

Second brain

The subject changes here. Levels 0 and 1 are about using Claude Code safely in any project. From Level 2 the trail describes one operator's personal setup around himmel: a notes vault, scheduled jobs, phone messaging and a health-data pull. It is optional, and nothing in Levels 0 and 1 depends on it. If you only want guardrails, you can stop at Level 1.

Connect a vault — the folder of Markdown notes defined at the top of this page. Start from the bundled , or connect a vault you already made from it; an arbitrary folder of notes is not enough (see ). Then pick which of the eight cadences to arm — the recurring scheduled jobs defined at the top of this page: the content pipeline (harvest, synthesize, health), the search reindex, the knowledge-graph refresh, a cleanup sweep (if you took the codex lane), the upstream drift-fix and upstream watch, and — only where they apply — a Windows repo sync and a Google Health pull. The search reindex is its own cadence with its own arming — arm only the pipeline and your search goes stale.

LEVEL 3

Reach: your phone joins

Wire the Telegram bridge. The installer also asks — explicitly, by name — whether the bridge should survive reboots, on the platforms where it has an installer for that (Windows and Linux).

Impact: ideas and alerts meet you where you are. The vault fills itself from your phone; the system can tap your shoulder when something needs you.

Needs a bot token; the wizard walks you through it and never echoes secrets.
LEVEL 4

Review depth

Add the optional review lanes — codex and hermes — beside Claude's built-in review. They are offered as review lanes: a second opinion on your diff before it merges. Each is its own explicit opt-in, with its own login.

Impact: two model families argue over your diff before it merges. The trade, plainly: without these lanes, review runs Claude-only — one reviewer, however good.

Skippable forever — and the wizard tells you at the question itself what skipping costs you.
LEVEL 5

Spend & context, under control

See and steer what agent work costs — tokens, quota windows, context — before it surprises you.

LEVEL 6

Always-on operations

Harden for unattended work: always-on hardening, handover state so work survives any single session, overnight runs, and a real monitoring stack — Grafana, Prometheus and himmel's own exporters, installed on your machine — feeding alerts to your bridge.

Impact: work continues while you're away. Instead of reconstructing the night, you read one morning report and make the decisions only you can make.

Partly guided-manual today: the installer wires the monitoring stack up on Windows, but reports it as not yet runnable elsewhere, and a few schedules are still armed by hand.
LEVEL 7

Command a fleet

Two words first, because the rest of this level uses them (both are defined in the glossary). A leg is one work session that owns exactly one ticket, in its own worktree. The console is the one session you keep in front of you: it reviews legs at their stop points, holds the sole authority to release a merge, and escalates to you only what genuinely needs you.

The summit is many legs running at once under one console. They coordinate through a written layer — mission briefs plus handover and roadmap documents every leg reads and appends — and by direct messages to the console when something is urgent.

A read-only console for watching it happen ships today: a local web UI showing fleet state, escalations and a live event stream. Dispatch and adjudication are not built yet — the console's own UI says so.

Impact: you stop being the bottleneck of one session. A night's work is many tickets shipped in parallel — and the morning report stays your single human surface.

Glossary

The words this page leans on, in one place. Fleet terms (leg, console, and the rest) are defined once, in the project's glossary; the entries below agree with it.

attestation
Proof of testing and review written into a commit message as trailer lines, for example Platforms tested: linux. The push gate checks for them.
cadence
A recurring scheduled job that himmel arms with your operating system's scheduler — a nightly search reindex, say. Level 2 lists the eight; you pick which to arm.
CR
Short for CodeRabbit, an automated pull-request review app. Also used loosely for the review comments (“CR findings”) a pull request collects from any reviewer.
console
The one session you keep in front of you when running several at once; it reviews the others and holds the authority to release a merge. See the glossary.
gate
A check that must pass before a commit, a push or a merge is allowed. Git gates run as git hooks; a refusal stops the step.
handover
A written note that lets a later session pick up where an earlier one stopped, so work survives any single session.
hook
A small script Claude Code runs automatically before or after it uses a tool. A hook can refuse the action, which is how himmel blocks an edit on your main branch. (Git has its own, separate hooks; himmel uses those for its gates.)
lane
A backend — an AI model and its tooling — that himmel can run work on. The optional review lanes (codex, hermes) give a second opinion on your diff. The /lanes command lists the ones available to you.
leg
One work session that owns exactly one ticket, in its own worktree. See the glossary.
panel
The group of reviewers — Claude, plus any review lane you switched on — that the /pr-check command asks to look at the same diff.
plugin
An add-on pack for Claude Code: slash commands, skills and hooks installed from a plugin marketplace.
slash command
A command you type inside a Claude Code session, starting with /, such as /worktree.
vault
A folder of Markdown notes, usually opened in Obsidian. Himmel's second-brain level works on a vault made from its bundled template.
worktree
A second working folder for the same repository, on its own git branch and sharing its history. Himmel does feature work in worktrees so your main branch is never edited directly.
