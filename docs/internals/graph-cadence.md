# Graph publish cadence — reference (HIMMEL-2095)

> The `HIMMEL-GraphPublish-Himmel` scheduler task, armed via
> `scripts/luna/graphmap-cadence.sh` alongside its four sibling tasks
> ([`docs/tooling-catalog.md`](../tooling-catalog.md) covers those). This page
> is the fuller reference for the fifth: `scripts/graphify/graph-cadence.sh`,
> its ledger, and its failure surfacing.

> **⚠ Currently refuses to run — HIMMEL-2654, unresolved.** `graph-cadence.sh`
> exits 2 unconditionally, before touching anything: its pipeline lock is not
> actually safe under concurrency (stale-lock takeover is not single-winner,
> and lock age alone can evict a still-running pipeline), so two concurrent
> runs can both `reset --hard` + `clean -fdx` the same worktree. Do **not**
> register the scheduled entry (`graphmap-cadence.sh arm`) until HIMMEL-2654
> lands — arming it today only gets you a task that fires and refuses every
> time. The guard, this note, and its test all get deleted together as
> HIMMEL-2654's own step 3, which is what makes that ticket's closure
> observable.

## Why this exists

himmel's own graphify graph (`graphify-out/graph.json`) is heavily used —
139 of 143 sessions on the day this was written, via the MCP tools or the
CLI — but nothing refreshed or published it on a schedule, so it silently
rotted (the shipped graph sat 36 commits behind `origin/main` when this was
written). Because refreshing was lean-invoke only
(`graph-refresh`/`graph-publish` skills, operator-triggered), the graph got
regenerated by hand and committed **straight to `main`** with a bare,
ticketless subject — bypassing the worktree/PR workflow every other change
in this repo goes through (`d05ef8ca` "update graphify", `913073df` ".",
`378c21f9`/`310646da` "graphify update"). `graph-cadence.sh` exists to remove
the reason that happened: an unattended runner that measures staleness,
refreshes, publishes via a PR, and auto-merges it through the sanctioned
chokepoint.

## What it does, in order

1. `git fetch origin` — safe: fetch only updates remote-tracking refs, never
   the checked-out branch or working tree, so it never disturbs a live
   session working in the primary checkout.
2. Reads `built_at_commit` out of the **shipped** `graphify-out/graph.json`
   (`origin/main`'s committed blob via `git show`, not whatever happens to be
   on disk).
3. Measures staleness as `git rev-list --count <built_at_commit>..origin/
   main` — **not** `--merges`. himmel squash-merges every PR, so
   `--count --merges` always returns 0 while the true distance is the real
   number.
4. Below `--threshold`: `action=skipped`, one ledger row, exit 0.
5. At/above threshold: `ast-update.sh` (the free, AST-only structural
   refresh), `graph-publish.sh` (open/refresh the publish PR), then
   `merge-on-green.sh` (`ARMAUTOMERGE=1`, the sanctioned auto-merge
   chokepoint) — all three against a **dedicated worktree**, never the
   primary checkout (see below). A failing refresh short-circuits the
   remaining legs (see `graph-cadence.sh`'s own header for why this diverges
   from `ggs-cadence.sh`'s "run every leg regardless" convention).

## Where it runs — the dedicated worktree

`graph-publish.sh` does `git checkout -B chore/graph-publish-<corpus> ...`
in whatever repo it is invoked from, and `ast-update.sh` writes tracked
`graphify-out/*` files into whatever corpus root it is given. Firing either
against the primary checkout from cron would switch the branch of a repo
live agent sessions are working in and leave its tracked `graphify-out/`
dirty — exactly the temptation that produced the manual bare commits this
ticket exists to stop.

So every mutating leg runs inside `~/.claude/graph-cadence/<corpus-slug>`
(himmel → `himmel`), created on demand via `git worktree add` off the
primary and force-synced to `origin/main` (`checkout -B` + `reset --hard` +
`clean -fdx`) at the start of every run. A worktree has its own HEAD/index
and never touches the primary's checked-out branch or working tree — proven
by `test-graph-cadence.sh`'s own primary-untouched assertion (branch, HEAD,
`git status --porcelain`, and `git worktree list`'s row for the primary
itself, all asserted byte-identical before/after a full run).

**Never `/tmp`**: a cleanup sweep reaping a live worktree registration out
from under git's `.git/worktrees/<name>` bookkeeping leaves the primary
checkout's `git worktree list` pointing at a hole. `~/.claude/graph-cadence/`
follows the same persistent-runner-home convention every sibling cadence in
this repo already uses (`graphmap-cadence.sh`'s own `~/.claude/graphmap-
cadence`, `ggs-cadence.sh`'s `~/.claude/graphify-cadence`).

The worktree's **dirname must equal the corpus slug**: `graph-publish.sh`
derives its PR branch name from `basename(git rev-parse --show-toplevel)`,
with no `--corpus-name` override. `graph-cadence.sh` names the worktree
accordingly *for exactly this reason*, so the branch name it predicts (and
hands to `merge-on-green.sh` as an explicit selector — never the default
"current branch", which would resolve to the worktree's own housekeeping
branch after `graph-publish.sh`'s `restore_branch` puts it back) matches
what `graph-publish.sh` actually creates.

## Arm / inspect / remove

**Do not run `arm` for this leg until HIMMEL-2654 lands** (see the notice at
the top of this page) — the task will register fine, but every scheduled
fire refuses immediately (exit 2) instead of doing anything.

Same three verbs as every sibling cadence, via the shared
`graphmap-cadence.sh` entry point — there is no separate arm command for
this leg:

```bash
bash scripts/luna/graphmap-cadence.sh arm        # registers all five tasks
bash scripts/luna/graphmap-cadence.sh arm --force  # replace an existing arm
bash scripts/luna/graphmap-cadence.sh status     # per-task ARMED/not-armed + run log
bash scripts/luna/graphmap-cadence.sh disarm     # removes all five
```

The publish leg is grouped with the free structural (AST) pair for
`--ast-only` purposes (HIMMEL-2071): it needs no backend credential, so
`--ast-only` arms/replaces it too, alongside the AST pair, while leaving the
weekly semantic pair untouched. Default schedule: **every 6 hours**,
anchored at `:35` past (Windows: `<Repetition><Interval>PT6H</Interval>`;
POSIX: `35 */6 * * *`) — 20 minutes clear of `HIMMEL-GraphMapAst-Himmel`'s
own `:15`-past hourly fire, wider than the AST pair's own 10-minute mutual
stagger, because this leg is not free-and-instant like the AST pair: it can
run `ast-update.sh`, open/refresh a PR, and drive `merge-on-green.sh`'s own
`check-ci` watch, all in one fire. Both legs would otherwise contend for
`ast-update.sh`'s HIMMEL-910 promote lock (skip-not-wait, so a collision is
a skipped-and-retried refresh next fire, not a failure — the wider offset
just makes that the exception rather than the rule).

## The ledger

Two ledgers, both written every run:

1. **`<handover-root>/.graph-cadence/ledger.jsonl`** — this leg's own,
   resolved via `scripts/lib/handover-path.sh`'s `handover_root` (never a
   literal path). One JSON line per run:

   ```json
   {"ts":"2026-09-06T14:34:57Z","head":"<origin/main sha>","graph_head":"<built_at_commit>","merges_behind":21,"action":"merged","pr":"https://github.com/.../pull/42","duration_s":36,"error":null}
   ```

   `action` is one of `skipped | failed | refreshed | published | merged` —
   see `graph-cadence.sh`'s header for the full classification (in short:
   `published`, not `failed`, ONLY when `merge-on-green.sh` exits with a
   documented time-resolving deferral — check-ci gate not green, or an
   indeterminate/retryable merge attempt (its own exit codes 14/15). Any
   OTHER non-zero `merge-on-green.sh` exit — a missing tool, an unwritable
   audit sink, a misconfigured base/privacy binding — is `failed`, not
   `published`: not every non-landing merge is a benign "not yet", and a
   permanently broken merge leg must not read as healthy forever).

2. **The standard flow-run ledger** (`~/.himmel/flow-runs.jsonl` by default,
   `scripts/lib/flow-run-ledger.sh`) — a `start`/`end` row pair under flow
   name `graph-publish-himmel`, the same mechanism every other cadence in
   this repo writes, so the existing cadence-audit/staleness tooling is not
   blind to this leg.

**`HANDOVER_DIR` is required, not optional** (HIMMEL-2619 class): cron gives
no login shell, so `HANDOVER_DIR` is exactly the variable that goes missing
there. If it is unset, `graph-cadence.sh` refuses **loudly** — non-zero exit,
a clear stderr message naming the variable, a line in the runner's own
per-fire log, and a flow-run-ledger row with `outcome:"error"` — rather than
let `handover_root_ensure` silently `mkdir -p` himmel's own `handovers/`
Mode-A stub and write the cadence ledger straight into the git repo it
publishes. Set it via `/handover-setup`, or see
[`docs/internals/handover-system.md`](handover-system.md).

## The standing ticket

Every publish PR's commit subject carries `[HIMMEL-2095]` — this repo's CI
commit-range gate requires a ticket ID on every commit, and the PR's subject
used to carry none at all (plausibly why the manual bypass was reached for
in the first place; see "Why this exists" above). `graph-publish.sh --ticket
<ID>` (default `HIMMEL-2095`, or `$GRAPH_PUBLISH_TICKET`) lets the standing
ticket change without editing code.

## The threshold, and its trade-off

Default **15** commits behind. Justified against the measured numbers: the
shipped graph was 36 commits behind `origin/main` when this was written,
with the operator refreshing by hand at irregular multi-day intervals. This
cadence fires up to 4×/day (every 6h). A threshold of 3 (this repo's typical
single-PR commit count) would open a publish PR on almost every run —
constant PR churn for a marginal freshness gain. 15 sits below half of the
measured 36-commit gap: it fires immediately at that staleness, and in
steady state bounds the graph's staleness to roughly "at most one busy day's
worth of merged PRs" rather than the previous unbounded, hand-triggered-only
gap, while still going quiet on days with only a handful of merges.

This is a starting point, not a measured optimum. Retune it by editing
`THRESHOLD=15` in `graph-cadence.sh` itself — the emitted runner's payload is
`bash graph-cadence.sh --corpus-root <path>`, with **no `--threshold` baked
in**, so it always falls through to the script's own current default. A
default change therefore takes effect on the **very next scheduled fire**,
with no re-arm needed. (`--threshold <N>` still exists for an ad-hoc manual
run against a different value — it just isn't what the armed cadence uses.)

## Where failures show up

- **The armed task's own run log** — `graphmap-cadence.sh status` surfaces
  it: `~/.claude/graphmap-cadence/graphmap-publish-himmel.log` (rotated to
  `.log.prev` each fire by the cron/schtasks wrapper `graphmap-cadence.sh`
  itself emits). This captures `graph-cadence.sh`'s **complete** stdout +
  stderr for the fire — fetch, `ast-update.sh`, `graph-publish.sh`,
  `merge-on-green.sh`, all of it — and is the log to check first during an
  incident.
  `graph-cadence.sh` also carries its own internal `LOG_FILE`
  (`~/.claude/graph-cadence/<corpus-slug>.log`, e.g. `himmel.log`) — but that
  path is written ONLY by the `HANDOVER_DIR`-unset refusal (a narrow,
  pre-worktree failure mode reached before the run log above even exists);
  it is not rotated and is not where a normal run's output lands. Don't
  confuse the two.
- **This leg's own ledger** (`<handover-root>/.graph-cadence/ledger.jsonl`)
  — `action:"failed"` plus the real error text. A failed *append* to this
  file is itself a hard failure (exit 4, distinct from every other code) —
  see `graph-cadence.sh`'s own exit-code table: the ledger IS the report, so
  a run that could not record itself is never read as a quiet success.
- **The standard flow-run ledger** — an `end` row with `outcome:"error"`.
- **`himmel-doctor.sh`**: a `C33-graph-stale` row (`check_c33_graph_stale`;
  the ID may have been renumbered again by the time you read this — check
  that function's own header) reads the ledger's last row and WARNs (never
  FAILs — an unpublished graph degrades query quality, it never breaks the
  harness) when the last run is older than 3× the armed interval, the last
  recorded action is `failed`, or the row's action is unrecognized/
  undetermined (a missing `jq`, or an unparseable row — "cannot tell" must
  never render as "healthy").

## Adding a second corpus (out of scope for v1)

himmel is the only corpus wired, and `--corpus-root` currently **refuses**
any value that doesn't canonicalize to the resolved primary checkout
(rc=1) — it is not a real multi-corpus switch today (PR-B panel r1,
codex-3): fetch, the shipped-graph read, staleness measurement, and the
dedicated worktree's *source* all still target `$HIMMEL_ROOT` unconditionally
inside the script, regardless of what `--corpus-root` is given. A flag that
looked like it worked and silently operated on the wrong repo was judged
worse than no flag, so it refuses instead.

To add a real second corpus: make those four internal uses of `$HIMMEL_ROOT`
(fetch, shipped-graph read, staleness measurement, worktree source) key off
`$CORPUS_ROOT` instead wherever the two can legitimately differ, verify that
end-to-end against a fixture repo (mirroring `test-graph-cadence.sh`'s own
hermetic pattern), THEN drop the refusal above; give the new corpus its own
worktree slug (`~/.claude/graph-cadence/<slug>`, matching that corpus's own
directory basename so `graph-publish.sh`'s branch-name derivation still lines
up) and its own scheduler task name (following the
`HIMMEL-GraphPublish-<Name>` convention).
